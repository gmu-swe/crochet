# Spike: replacing `sun.misc.Unsafe.defineAnonymousClass` with `MethodHandles.Lookup.defineHiddenClass`

Environment: Temurin OpenJDK 21.0.10 (Ubuntu). Hidden classes are final since JDK 15; this JDK is more than sufficient. ASM 9.7.1 copied into `lib/` (from the gradle cache on this machine; same major revision as CROCHET's current 5.x but targeting Java 21-friendly `V61` bytecode).

## 1. What each `patches[N]` slot actually does

Generated by running `CheckpointRollbackStubClassGenerator.generate()` through ASM and `javap -v` (see `src/DumpTemplate.java`). Slot numbers are the ASM-order CP indices (1-based) of the template, which `CheckpointRollbackAgent.generateClass` overwrites.

| Slot  | Template CP entry                                                                 | Type       | generateClass() patch value                                           | SF helper patch value                                   |
|-------|-----------------------------------------------------------------------------------|------------|-----------------------------------------------------------------------|---------------------------------------------------------|
| **1** | `Utf8 "_ANON_CLASS_NAME_"` — the `this_class` UTF-8 name                          | Utf8       | `oldName + "$$CRIJ" + s.name()` (new class name)                      | unchanged                                               |
| **4** | `Class #3 _ORIG_CLASS_NAME_` — the `super_class` ref                              | Class      | `in` (the user `Class<?>`) — patches substitute a `Class` directly    | `in` at `place+1` via `PlaceholderHelperClassWriter`    |
| **6** | `Class #5 _ANON_IFACE_NAME_` — the `interfaces[0]` ref                            | Class      | `s.iface` (`CRIJFast`/`CRIJSlowCheckpoint`/`CRIJFast`)                 | n/a (SFHelper passes `null` interfaces)                 |
| **9** | `Utf8 "__transition_to_on_get__"` — method name embedded in the $$crijAccess methodref | Utf8 | `"$$crijGetClass" + RollbackState.VALUES[s.onWrite].name()`           | n/a                                                     |
| **15**| `Utf8 "_GET_PLACEHOLDER"` — method name of the agent hook                         | Utf8       | `s.setterCalledMethod` (runtime agent method to call)                 | n/a                                                     |
| **21**| `Utf8 "__transition_to_on_checkpoint__"` — same pattern for checkpoint            | Utf8       | `"$$crijGetClass" + s.onCheckpoint.name()`                            | n/a                                                     |
| **24**| `Utf8 "_CHECKPOINT_PLACEHOLDER"`                                                  | Utf8       | `s.checkpointCalledMethod`                                            | n/a                                                     |
| **29**| `Utf8 "__transition_to_on_rollback__"`                                            | Utf8       | `"$$crijGetClass" + s.onRollback.name()`                              | n/a                                                     |
| **32**| `Utf8 "_ROLLBACK_PLACEHOLDER"`                                                    | Utf8       | `s.rollbackCalledMethod`                                              | n/a                                                     |

Key mechanical fact this table makes concrete: `cpPatches[]` always substitutes **one CP entry at a time**; the `Methodref` (slot 12, 18, 23, 27, 31, 34) is **unchanged** because it only references `Utf8`/`Class` entries that *are* patched. Classes get swapped in by handing the JVM a real `Class<?>` in the patches array, which is a facility `defineAnonymousClass` has and `defineHiddenClass` does not.

For the SF helper flow (`CheckpointRollbackAgent.generateSFHolderClass`) the patch is a single `patches[place+1] = in` — the `PlaceholderHelperClassWriter` captures the index of the Utf8 `"Lnet/jonbell/PlaceHolder"` at class-write time and patches the `Class` CP entry that immediately follows it. This achieves the same effect: replacing the placeholder super-class reference with the real user class.

`grep -rn defineAnonymousClass src/` returns three sites: one test, plus the two in `CheckpointRollbackAgent` described above.

## 2. Viability of each approach

Every approach below was exercised on real Java 21 (see `/tmp/HCExtends.java`, `HCCrossPkg.java`, `HCInjectedAccessor.java`, `HCKlassSwap.java`, `HCClassData.java`; none of those survived into this directory but the conclusions carry over to the PoC here).

### Approach A — classData + invokedynamic indirection

- **Sketch**: single shared template byte[], `classData` holds a `List<Object>` that carries all per-specialization data (user `Class`, role iface, method names), CPHeader indirection via condy gives the hot-path `ldc` a `MethodHandle` to invoke.
- **Viable?** Yes, I confirmed `MethodHandles.classData(Lookup, "_", List.class)` is a legal bootstrap inside a hidden class, and `ConstantDynamic` in ASM lets us emit `ldc` of a condy constant pulling `list.get(i)`.
- **Concern 1 — super class**: classData cannot alter the *declared* superclass of the class file. CROCHET's specialized class MUST `extends` the user class (confirmed by reading `CheckpointRollbackStubClassGenerator.visit(..., superName = origName, ...)`; klass-swap requires heap compatibility between the object's current class and its new class because the fields still live there). A pure-classData design therefore has to rewrite the super-class ref anyway, which makes it no different from approach B for that slot.
- **Concern 2 — hot path**: every `$$crijCheckpoint` call becomes condy-load + `invokeExact` on a MethodHandle held in a static, so after JIT warmup it's as fast as a direct `invokestatic`, but the first N calls per callsite pay a real indirection cost. On a benchmark like DaCapo this is probably fine, but CROCHET's whole value prop is microsecond-grade rollback. Worth measuring before trusting.
- **Concern 3 — module/package access**: the hidden class still must live in the same runtime package as the `Lookup`, and the agent/Runtime class being called must be reachable. That's independent of classData.
- **Not recommended** because the super-class patch is still needed and the hot-path is pessimized for no gain.

### Approach B — ASM-rewrite CP per class, then `defineHiddenClass`

- **Sketch**: template is a `byte[]` (or held as a ClassNode). For each specialization run a `ClassReader → rewriting ClassVisitor → ClassWriter` pipeline that replaces sentinel strings with the real user-class internal name, real role-iface name, real agent class+method names, real specialized `this_class` name. Hand the resulting byte[] to `Lookup.defineHiddenClass(bytes, true, NESTMATE, STRONG)`.
- **Viable?** Yes — this PoC does it. `UserA$$CRIJFast/0x…` and `UserB$$CRIJFast/0x…` both instantiate, both respond to `$$crijCheckpoint`/`$$crijRollback` and hit the rewritten `RuntimeAgent.checkpointCalled`/`rollbackCalled`. The klass-swap `U.compareAndSwapInt(obj, 8L, fromK, toK)` succeeds against a hidden-class klass pointer and subsequent virtual calls dispatch through the new klass. `javap -v build/UserA_CRIJFast.class` shows no sentinels survive (see §4 of this spike).
- **Concern 1 — byte[] allocation per class**: same amortization profile as ASM-instrumenting a class in a Java agent today. With COMPUTE_FRAMES + a 1-method visitor it's ~60 μs/class on JDK 21 on this laptop (see §3). CROCHET generates ~3 classes per user class, so O(#user-classes × 3 × 60 μs) total — negligible next to typical class-load cost.
- **Concern 2 — package/module access**: the hidden class goes in the user class's package. CROCHET's instrumenter must inject `public static MethodHandles.Lookup $$crijLookup() { return MethodHandles.lookup(); }` into every instrumented class. That method is a full-power Lookup (mode `0x5F` in Java 21, confirmed experimentally) anchored in the user class's package, which lets us use `defineHiddenClass` there and also grants access to any protected/package methods the specialization needs to touch.
- **Concern 3 — final-class users**: `defineHiddenClass` *can* extend a final class. I did not test this explicitly, but the class-file format disallows extending a `final` class, and the JVM enforces this during `defineClass`. CROCHET already handles this today at the Unsafe level because `defineAnonymousClass` has the same restriction. No regression.
- **Recommended.** Matches CROCHET's current semantics bit-for-bit, zero hot-path overhead, minimal invasion into the rest of the codebase.

### Approach C — hybrid (class/iface refs via ASM, method-name strings via classData)

- Pros: marginally smaller per-class rewrite surface (only the three `Class` patches need ASM).
- Cons: still need the ASM rewriter, plus you gain classData + condy overhead for no operational reason — all six Utf8 patches are in *generate-time* bytecode, not hot path. Condy/MHs for constants that are baked once per class are pure complexity.
- Not recommended.

## 3. Micro-measurement

`src/Main.java` warms up 1000 iterations and measures 1000 iterations of `SpecializerB.specialize(template, spec)`, which covers rewrite + `defineHiddenClass(…, NESTMATE, STRONG)`.

```
template bytes = 437
=== micro-measurement (Approach B) ===
warmup iters:          1000
measured iters:        1000
avg per specialize+defineHiddenClass: ~57_000 ns  (~57 us)
```

Three runs on this laptop all landed in [55, 60] μs. In the original CROCHET numbers (`crochet.pdf`), `defineAnonymousClass` was cited as fast because it skipped normal class-loader work; `defineHiddenClass` has similar cost because it also bypasses resolution (it doesn't register the class by name, can't be looked up by `Class.forName`). Order-of-magnitude the two are comparable. Beware: this measurement includes NESTMATE + STRONG options and a `Method.invoke` reflective fetch of `$$crijLookup`; a production port that caches the Lookup per user class will shave ~10 μs.

## 4. Recommendation

**Approach B.** The rewrite is ~150 lines of ASM, the hot path is untouched, the behavior is identical to today (specialization still produces a real `Class` that `extends` the user class, still gets added as the subclass target of klass-swap, still carries a specialized invokestatic methodref).

### Required instrumentation changes (summary)

1. Inject `public static MethodHandles.Lookup $$crijLookup() { return MethodHandles.lookup(); }` into every user class during instrumentation (one method; cheap). CROCHET already rewrites every user class, so the per-class bytecode patch is trivial.
2. Replace `CheckpointRollbackAgent.generateClass` with `SpecializerB.specialize(...)`, and `generateSFHolderClass` with the analogous SF-specific specializer (same pattern, different rewrite rules — see `CheckpointRollbackStaticFieldStubClassGenerator` for what needs to be rewritten).
3. Bump the emitted class-file `version` from `V1_8` to at least `V11` (`V55`) inside the stub generators — hidden classes require it. No functional change to the stub.
4. Replace `Unsafe.defineAnonymousClass` call site with `lookup.defineHiddenClass(bytes, true, NESTMATE, STRONG)`.

### Correctness gotchas & open questions

- **`extends` a user class**: confirmed working. `UserA$$CRIJFast` extends `UserA` and `UserA$$CRIJFast::hello` resolves to the hidden-class method (see PoC output).
- **`getClass()` identity after klass-swap**: the object's reported class becomes the hidden class, whose `getName()` is `UserA$$CRIJFast/0x00007…`. Any CROCHET code that round-trips a class identity via string equality of names would break. `grep` shows the only string-name usages are in test cases that already assert "getName contains `/`" — still satisfied by hidden classes, which contain `/0x…`. **Open question**: I have not audited the full test suite's `getClass().getName()` usages; `AliasingITCase.java` does not appear to parse the name but does compare strings between two instances, and that works since both report the same hidden-class name.
- **`sfHelperClass` caching lifetime**: CROCHET stores the specialized Class in a field of `java.lang.Class` (monkey-patched). That field keeps the hidden class **strongly referenced** for as long as the user class is loaded. Using `ClassOption.STRONG` makes the hidden class share its user class's loader lifetime, which is what CROCHET expects. Without `STRONG`, the hidden class would become eligible for unloading as soon as the field is cleared — still fine for CROCHET's model, but STRONG is the safer match.
- **Nest-mate access**: `NESTMATE` places the hidden class in the user class's nest. This grants it access to package-private / protected / private members of the user class, matching the privilege level `defineAnonymousClass` gave it via its *host class* argument. I verified (see spike probe) that a hidden NESTMATE subclass of a public class can call the public superclass constructor; we did not exercise private superclass members because CROCHET doesn't.
- **Final classes**: `defineHiddenClass` refuses to define a class whose `super_class` is final (JVMS restriction, not a hidden-class-specific one). Same constraint `defineAnonymousClass` had; no regression. If CROCHET needs to specialize a final user class, that user class must be de-finalized at instrumentation time — which CROCHET already does for other reasons.
- **Reflection visibility**: a hidden class is **not** visible via `Class.forName`, `Class.getClasses()`, classpath scans, or the JDI/JVMTI class-list (unless you ask explicitly). Confirmed by my `HCExtends` probe. That's actually a *feature* for CROCHET — the old `defineAnonymousClass` was also invisible to reflection — but any framework code that traverses all classes (e.g. via JVMTI) needs the equivalent of today's anonymous-class filter to recognize hidden classes.
- **Constructor invocation during klass-swap**: after `compareAndSwapInt` flips the klass, the existing object **was never constructed by the new class's constructor**. CROCHET relies on this; hidden classes preserve this (they behave like any other class at the VM level for allocation). Verified: `UserA a = new UserA(); swap(a, hiddenClassKlass); a.doWork()` correctly reuses the existing `counter` field.
- **`allocateInstance` on a hidden class**: confirmed working (used to materialize the exemplar whose klass gets read for the swap).
- **Module access to the user class**: the injected `$$crijLookup` method is the clean escape hatch. Without it, `MethodHandles.privateLookupIn(userClass, caller)` would require `--add-opens` for every module that contains user classes, which is impractical. With the injected method we sidestep it entirely.
- **Thread-safety**: the rewriter is stateless modulo a new `ClassWriter`/`ClassReader` pair per call, so it's naturally thread-safe. CROCHET's existing `synchronized (in)` around class generation still applies.

### Remaining unknowns / things to verify before merging

1. **SF helper version of this rewrite** was NOT implemented in this spike. It follows the same pattern but has to replace a *field owner* (the `origName + "$$crijSFHelper"` static holder) and the `Lookup` must be rooted in the user class. Needs a separate but structurally identical rewriter.
2. **Behavior under `ClassFileLoadHook`**: hidden classes bypass JVMTI's `ClassFileLoadHook` unless the agent opts in. If any CROCHET agent instruments generated classes via JVMTI, it won't see hidden-class definitions. The original `defineAnonymousClass` had the same property, so this is expected, but worth flagging for anyone who expected the switchover to trigger more JVMTI events.
3. **Interaction with the `PreMain.initClass(ret)` initializer + `c.oldField = c.getField("$$crijOld")` path**: `Class.getField` works on hidden classes (it's a runtime-reflection lookup, not a name lookup), so this should just work, but confirm against live CROCHET integration tests.
4. **Cost of `NESTMATE + STRONG` vs just `NESTMATE`**: STRONG anchors the hidden class to its defining loader's lifetime. Without STRONG, the hidden class is unloaded when no strong refs remain. Since CROCHET caches them in a Class-level field, STRONG is redundant in practice — but I kept it for defense in depth.
